# retail-stats-rules（規約スキル）

出自: `docs/design/loop-engineering-design.md` §3.2 / §3.3。`paths` を設定して
**パーサ編集時にのみ自動発動**する（常時ロードするとコンテキストを恒常的に
消費するが、規約が必要なのはコードを触るときだけ）。

---

## R1. カタログ駆動の禁則（FR-03 / FR-24 / NFR-09）

**業態名・指標名・別名をコードに一切書かない。**

```python
# NG — カタログに書くべきものがコードに漏れている
if "ショッピングセンター" in title:
    segment_id = "shopping-center"

# OK — catalog.py が唯一の読取口。ID はカタログ経由でしか得られない
for alias, segment_id in catalog.segment_alias_index():
    if alias in normalized:
        ...
```

- カタログに無い ID をコードが生成する経路を持たない
- 指標の増減が**コード変更を伴わない**こと（NFR-09）が守れているかを、
  ルール追加のたびに自問する
- 発表主体コードも同様。`meti` / `sc-association` 等を条件式に直書きしない
  （唯一の例外は要件 IF-02 が定める**記事側の発表主体マーカー**の検出語で、
  これは `parser.resolve_authority()` の 1 箇所に閉じる）

## R2. 推測でラベルを付けない（FR-24 / カタログ §2.2）

`parse-wbs.py` の `infer_*_from_*()` 系は**移植しない**。WBS は欠損値を推測で
埋めてよいが、本システムは推測でのラベル付けを禁じている。

**最重要**: 記事本文に「既存店」の文字列が**ない**限り、既存店指標として扱わない。
実務上、既存店表記のない見出しを既存店統計として扱うことが最も頻発する誤読
（カタログ §3-1）。`§2.1 の既定スコープ` は metric_id が決まった**後**に
scope を割り当てる値であり、metric_id の決定には関与しない。

## R3. 未解決を捨てない（FR-10 / 要件 7-12）

解けなかった行は必ず `unresolved` に落とす。**0 件返して静かに済ませない。**
これがこのプロジェクト最大の危険（silent accumulation, §1.2）への唯一の防波堤。

判別できないもの（ヘッダかデータか分からない行など）も落とす側に倒す。

## R4. 正規表現の落とし穴

### `\b` を CJK の境界に使わない

```python
>>> re.search(r"505\b", "505億円")     # None（CJK の直前に単語境界がない）
>>> re.search(r"505\b", "505 yen")     # マッチする
```

桁区切りカンマの除去は `(?=[0-9]{3}(?![0-9]))` を使う。`\b` 版は実データで
発火せず、`1兆4,505億円` を **505.0**（正しくは 14505.0、約 30 倍の誤差）として
取り込む。**例外にも未解決行にもならない**ため、テストで固定しない限り気づけない。

### 全部任意の正規表現は空文字にマッチする

`VALUE_JPY_RE` は 兆 / 億 / 万 が全て任意のため空文字にも一致する。
`finditer` の結果は「`cho` / `oku` / `man` のいずれかが非 None」で必ず絞る。

### 狭いパターンから先に評価する

期間表記の判定順は `半期 → 決算期 → 年度 → 四半期 → 月次`。`1~6月期`（半期）は
`[0-9]{1,2}月期`（決算期）にも `[0-9]{1,2}~[0-9]{1,2}月`（四半期）にも一致する。
順序を誤ると半期が構造的に 0 件になる。

### 正規化後の文字列で表記ゆれを探さない

`textnorm.normalize()` は NFKC で全角％を `%` に、`ヶ月` を `カ月` に潰す。
**正規化後の文字列から表記ゆれを探すと必ず 0 件になる。** 表記ゆれの検出は原文で行う。

## R5. 正規化の順序を変えない（FR-05 / 実装設計 §4.2）

`textnorm.normalize()` の 5 段階は順序依存。順序を変えると結果が変わる。
テスト（T-3 の正規化表）で順序が固定されている。

元のタイトルは破棄しない。`title_first_seen` / `title_variants` は原文で保持し、
正規化文字列はパース中のみ使う。`raw_expression` も原文からの切り出しとする。

## R6. 実行時刻を持ち込まない（NFR-06）

永続化される全レコードのタイムスタンプは**掲載日（ファイル名の日付）由来**。
`datetime.now()` を parser / period / store で呼ばない。`period.py` は掲載日を
**引数で受け取る**（グローバル日時に触れない）。

走査順に依存する出力を作らない。代表 variant の選択、別名索引の順序、
upsert の収束はいずれも順序非依存でなければならない。

## ルール追加の手続き（規律 G2。**これを省略しない**）

正規表現ルールを 1 本追加するごとに、コミットメッセージに 3 点セットを残す。

| # | 記録すること |
|---|---|
| 1 | **そのルールが対象とする実データの行**（原文を引用） |
| 2 | **追加前後の未解決件数**（`python3 -m retail_stats measure` の実測） |
| 3 | **誤抽出を増やしていないこと**（golden ケースが引き続き通ること） |

推測で書かない。実データの分布から書く。

## 未解決率を下げる方法は 3 つあり、正しいのは 1 つだけ

| 手段 | 効くところ | 正当性 |
|---|---|---|
| 正規表現ルールを増やす | 分子を減らす | **正しい** |
| confidence 閾値を下げる | 分子を減らす | **誤り**。誤抽出が増える（⑧ T1 が検出） |
| 取りこぼしを `out_of_scope` に付け替える | 分母を縮める | **誤り**。取りこぼしが正当化される（⑧ T3 が検出） |

後ろ 2 つは数値上は改善に見え、grep でも見つけにくく、AI にとっては圧倒的に簡単。
**件数と原文は保持されるため FR-10 の検査は通ってしまう。**

## テストの書き方

- ランナーは標準ライブラリの `unittest`（pytest は導入しない）
- パーサのテストは「タイトル文字列 → Observation」の**純関数テスト**として書く。
  ファイル I/O を伴わせない（`parser.py` が `store.py` に依存しない理由）
- 入力は必ず `tests/fixtures/` から取る。実データを直接読むテストは再現性を持たない
- 金額換算のように**例外を出さずに誤値を返す**経路は、必ずテストで値を固定する
