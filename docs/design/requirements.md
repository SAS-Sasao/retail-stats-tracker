## 1. 概要

### 1.1 背景

- `domain-tech-collection` 組織では 2026-03-21 以降、日次ダイジェスト（`/company-daily-digest`）を毎日自動生成しており、2026-07-25 時点で 101 日分の MD が蓄積している
- そのうち「決算・統計」章には、業態別・企業別の月次統計記事が延べ **588 行**（うち一意 URL **405 件**）蓄積されている。1 日あたり最大 15 行（2026-05-25）、次点 14 行（2026-06-26）、平均約 6.8 行[^count]
- 記事タイトルには数値がそのまま含まれており、例えば `ショッピングセンター／6月既存店売上1.6％減、夏物振わず51カ月ぶりに前年割れ`（2026-07-25 / 流通ニュース）のように、業態・対象月・指標・値・方向の 4 要素が 1 行に凝縮されている
- しかし現状は MD の日付ファイルに分散しており、「SC の既存店前年比を 4 月から 6 月まで並べる」といった時系列比較ができない。数値は取得済みなのに活用されていない状態にある
- 一方で同一記事が複数日にわたり重複掲載される。実測の最大は URL `s041442` の **6 日**（2026-04-15 / 16 / 17 / 18 / 22 / 23）で、次いで `s071772`（PPIH 6 月既存店）などが 4 日分に出現する。延べ 588 行に対し一意 URL は 405 件であり、**183 行（31.1%）が重複掲載**。単純結合では重複カウントが発生する

[^count]: **計測日**: 2026-07-25。日次ダイジェストは毎日追加されるため、これらの実測値は計測日により変動する（設計書は 2026-07-26 時点の 102 ファイル / 595 行 / 一意 406 件で記述している。差の内訳と扱いは 7.1 の注記を参照）。集計条件 — 対象は `docs/daily-digest/*.md`（2026-03-21 〜 2026-07-25 の 101 ファイル）。**見出しテキストに「決算・統計」を含む `###` セクション**の配下のみを走査し、次の `###` 見出しで打ち切る。そのうち `^\| *[0-9]+ *\|` に一致する行をデータ行として計数した（ヘッダ行・区切り行・「該当する記事はありませんでした」は除外）。一意 URL は行中の `https?://` 以降を抽出して重複排除したもの。同条件で見出しを章番号（`### B5.`）に置き換えると **延べ 590 行 / 一意 407 件 / データ行を持つファイル 88** へ過大計上される。増分の実体は 2026-03-26 の `B5. データ活用・DX` の 2 行が混入すること。2026-03-24 の `B5. EC・オムニチャネル` は番号付きリスト形式でありデータ行としては計上されないが、章番号判定では対象セクションとして誤検出される（7-1 の制約に対応）。

### 1.2 目的

1. 日次ダイジェストの「決算・統計」章を機械的にパースし、業態 × 対象期間 × 指標の時系列データセット（JSON）を構築する
2. 業態別トレンドを比較閲覧できる静的 HTML を生成し、GitHub Pages で配信する
3. SIer 提案時に「なぜこの業態に DX 投資すべきか」を自前の観測データで語れる状態を作る。外部レポートの引用ではなく、出典 URL 付きの一次情報リンクを添えて主張できることを到達点とする

### 1.3 スコープ

| 区分 | 内容 |
|------|------|
| スコープ内 | 決算・統計章のパース、指標カタログ駆動の正規化、時系列 JSON 生成、冪等な再取り込み、静的 HTML 生成（業態別トレンド・指標比較・出典一覧・データ品質）、GitHub Actions による日次自動更新 |
| スコープ外（v0.1） | 外部 API・Web スクレイピングによる数値の直接取得、記事本文の取得、B5 章以外（B1〜B4 / A 章）のパース、予測・回帰などの統計モデリング、複数組織横断の集計、動的検索 API・サーバーサイド処理、ユーザー認証 |

### 1.4 システム構成概要

```
[入力: 既存 MD のみ]                [バッチ (Python / GitHub Actions)]        [出力: 静的配信]

.companies/domain-tech-collection/
  docs/daily-digest/*.md ──────▶  ① セクション抽出
     (101 日分 / 日次追加)            「決算・統計」見出しを検出
                                          │
  docs/retail-domain/                     ▼
  retail-monthly-kpi-catalog.md ─▶  ② 正規化辞書ロード
     (業態 / 指標 / 別名の定義)         segment・metric・別名・単位
                                          │
                                          ▼
                                   ③ 決定論パース (regex)
                                     confidence 付与
                                          │
                              ┌───────────┴───────────┐
                              │ conf >= 閾値           │ conf < 閾値 / 未解決
                              ▼                       ▼
                          ④ 確定                  ⑤ LLM 抽出フォールバック
                              │                    （URL 単位・結果キャッシュ）
                              └───────────┬───────────┘
                                          ▼
                                   ⑥ 冪等 upsert
                                     natural key で重複排除
                                          │
        .companies/.../docs/retail-stats/data/  ◀── 中間データ・抽出キャッシュ
          observations.json / articles.json          （組織スコープ・証跡）
          extraction-cache.json / unresolved.json
                                          │
                                          ▼
                                   ⑦ 単一 HTML 生成
                                     JSON インライン埋め込み
                                     Chart.js インライン
                                          │
                                          ▼
                              docs/retail-stats/index.html  ──▶ GitHub Pages
```

- パイプラインは **入力が MD ファイルのみ** の閉じたバッチ。ネットワークアクセスは LLM 抽出フォールバック（⑤）を除き発生しない
- ⑥ の upsert により、同一の業態 × 期間 × 指標は常に 1 レコードに収束する（1.1 の重複掲載への対処）
- 配信物は単一 HTML。外部 CDN・fetch に依存せず、`file://` で開いても動作する自己完結構成とする

## 2. 機能要件

### 2.1 取り込み・パース系

| ID | 機能名 | 内容 | 優先度 |
|----|--------|------|--------|
| FR-01 | 対象セクション抽出 | `docs/daily-digest/*.md` を走査し、**見出しテキストが「決算・統計」である `###` セクション**の表行を抽出する。章番号（B5）では判定しない（後述 7-1 参照） | 必須 |
| FR-02 | 表行のトークン化 | `\| # \| 記事 \| ソース \| 要約 \|` 形式の行から、記事タイトル・出典 URL・ソース名・要約を分離する。列数・列順はヘッダ行から動的に解決する | 必須 |
| FR-03 | 指標カタログ読込 | 業態区分・指標定義を `docs/retail-domain/retail-monthly-kpi-catalog.md` から読み込む。**業態名・指標名をコードにハードコードしない**（IF-02 のスキーマ契約に準拠） | 必須 |
| FR-04 | 決定論パース | 正規表現ルールで 業態 / 対象期間 / スコープ / 指標 / 値 / 方向 を抽出し、抽出根拠と confidence（0.00–1.00）を付与する | 必須 |
| FR-05 | 表記ゆれ正規化 | 全角％と半角%（決算・統計章 588 行での実測は ％ = 226 件 / % = 631 件で混在）、全角数字、`／` 区切り、`増 / 減 / 上昇 / 増加 / 前年割れ / 横ばい` の方向語、`カ月 / ヶ月` を正規化する | 必須 |
| FR-06 | 期間解決 | 記事タイトルの相対表現を絶対期間に解決する。掲載日（ファイル名の日付）を基準に、`6月`→`2026-06`（月次）、`2月期`→`FY2026-02`（決算期）、`3〜5月`→四半期、`2025年度`→年度 として period_type 付きで格納する | 必須 |
| FR-07 | LLM 抽出フォールバック | FR-04 で未解決、または confidence が閾値（既定 0.70）未満の行のみ、LLM に構造化抽出を依頼する。出力は observations と同一スキーマの JSON。スキーマ検証失敗時は 1 回だけ再指示リトライする | 必須 |
| FR-08 | 抽出結果キャッシュ | LLM 抽出の結果を出典 URL のハッシュをキーに永続キャッシュする。既にキャッシュがある URL は再抽出しない（冪等性・コスト・実行時間の全てに効く） | 必須 |
| FR-09 | 冪等 upsert | natural key `(segment_id, metric_id, scope, period_key, source_authority)` で upsert する。既存レコードがある場合は confidence が高い方を採用し、同値なら掲載日が新しい方を採用する。**発表主体が異なる観測は別レコードとして共存させる**（母集団が異なる別の量であり、上書きしてはならない。7-14 参照） | 必須 |
| FR-10 | 未解決行の退避 | どの手段でも構造化できなかった行を `unresolved.json` に理由コード付きで退避する。破棄しない（silent fail 禁止） | 必須 |
| FR-11 | 複数指標の分解 | 1 記事タイトルに複数指標が含まれる場合、複数 observation に分解する。例: `日本百貨店協会／6月の外国人売上29.8％増、客数0.5％減・客単価30.4％増` は 3 レコードになる | 高 |
| FR-12 | 増分実行 | 前回実行以降に追加・更新された MD のみを処理するモードと、全件再構築モード（`--rebuild`）の双方を提供する | 高 |

### 2.2 出力・可視化系

| ID | 機能名 | 内容 | 優先度 |
|----|--------|------|--------|
| FR-13 | 時系列 JSON 生成 | observations を業態 × 指標 × 期間で整形した配信用 JSON を生成する | 必須 |
| FR-14 | 単一 HTML 生成 | データ JSON と描画スクリプトをインライン埋め込みした単一 HTML を生成する。外部 CDN 参照・実行時 fetch を行わない | 必須 |
| FR-15 | 業態別トレンド表示 | 業態を選択し、指標の時系列折れ線を表示する。複数業態の重ね合わせ比較ができる | 必須 |
| FR-16 | 指標横断比較 | 1 指標（例: 既存店売上前年比）について業態を同一チャートに並べ、業態間の格差を可視化する。並べる対象は**集計粒度と発表主体が揃った業態に限る**。集計粒度の異なる系列（`meti-commerce-dynamics` =「小売業全体」）は既定で除外する（表示不能にはせず、明示的に指定した場合は単独系列として表示できる）。粒度が 1 段違う系列を業態別の格差比較に混ぜると、本要件が可視化しようとしている格差そのものを誤読させるため。除外・単独表示の具体規則は設計書 §6.4 R6〜R8 を参照 | 必須 |
| FR-17 | 出典リンク | すべてのデータ点から出典記事 URL と初出掲載日に到達できる。提案資料での引用に耐えるトレーサビリティを担保する | 必須 |
| FR-18 | データ品質パネル | 抽出成功率、LLM フォールバック率、未解決件数、業態別の欠測期間を表示する | 高 |
| FR-19 | CSV エクスポート | 表示中のデータセットを CSV でダウンロードできる（クライアント側の Blob 生成のみ、サーバー不要） | 中 |
| FR-20 | 欠測の明示 | データが存在しない期間を線で補間せず、欠測として明示する。連続していない系列を連続に見せない | 必須 |

## 3. 非機能要件

| ID | 分類 | 要件 | 目標値 |
|----|------|------|--------|
| NFR-01 | 性能 | 全件再構築（101 日分・588 行）の実行時間 | LLM フォールバックがキャッシュ済みの状態で 60 秒以内 |
| NFR-02 | 性能 | 日次増分実行の実行時間 | 30 秒以内（LLM 呼び出し込み） |
| NFR-03 | 性能 | 配信 HTML の初期表示 | 1.5 秒以内。HTML 総サイズは 2 MB 以内（3 年分の増加を見込んだ上限） |
| NFR-04 | 正確性 | 決定論パースの単独カバー率 | 主要 4 業態（SC / 百貨店 / チェーンストア / コンビニ）の月次既存店指標で 90% 以上 |
| NFR-05 | 正確性 | **対象内行**の抽出成功率（未解決率の裏返し） | 80% 以上。未解決 20% 以下を維持し、超過時は正規表現ルールの追加で対処する。**分母は「発表主体が協会統計・マクロ統計である行」**とし、個社決算・個社月次の記事および小売月次統計でない一般記事は `out_of_scope` として分母から除外する（7-15 参照）。除外は silent fail にせず件数を SC-06 に表示する（NFR-10） |
| NFR-06 | 再現性 | 同一入力に対する出力の一致 | 抽出キャッシュが存在する限り、再実行で JSON がバイト一致すること（LLM の非決定性をキャッシュで封じ込める） |
| NFR-07 | 冪等性 | 重複掲載への耐性 | 同一記事が N 日に掲載されても observation は 1 件。**実測の最大重複数は 6 日**（`s041442` = 2026-04-15 / 16 / 17 / 18 / 22 / 23）であり、この非連続 6 日ケースをテストケースに含める。連続日のみを想定した実装にしない |
| NFR-08 | 自己完結性 | 外部依存 | 配信 HTML は外部ネットワークアクセス無しで全機能が動作すること。CSP `default-src 'self'` 相当の環境で成立させる |
| NFR-09 | 保守性 | 指標追加のコスト | 新規指標・新規業態の追加はカタログ MD の追記のみで完結し、パーサのコード変更を要しないこと（別名パターンの追加はカタログ側の列で表現する） |
| NFR-10 | 可観測性 | 実行ログ | 行単位の抽出結果（成功 / フォールバック / 未解決）を理由コード付きで出力する。`2>/dev/null` や `\|\| true` によるエラー握り潰しを禁止する |
| NFR-11 | コスト | LLM 利用 | 1 日あたりの新規 LLM 抽出対象は数行に収まる想定。キャッシュヒット率 95% 以上を維持する |
| NFR-12 | 可用性 | 配信 | GitHub Pages に依存。バッチ失敗時も前回生成の HTML が配信され続けること（生成失敗時に成果物を空で上書きしない） |
| NFR-13 | アクセシビリティ | 表現 | 系列の識別を色のみに依存させない（線種・マーカー・凡例テキストを併用）。増減は矢印記号ではなく符号付き数値とテキストで表す |
| NFR-14 | 互換性 | ブラウザ | Chrome / Edge / Safari の最新 2 バージョン。デスクトップ優先、タブレット幅まで対応 |
| NFR-15 | データ保護 | 取り扱い | 入力は公開記事の見出しと URL のみ。個人情報・顧客固有情報を含めない |

## 4. データ定義

永続化は RDB ではなく **JSON ファイル群**とする（3-8 の自己完結性、および GitHub 上で差分レビュー可能であることを優先）。以下の「テーブル」は JSON の論理スキーマを指す。

### 4.1 エンティティ一覧

| エンティティ | 役割 | 主なライフサイクル |
|-------------|------|-------------------|
| Segment | 業態区分（SC / 百貨店 / チェーンストア / コンビニ / SM / ドラッグ 等） | カタログから読込。システムは生成しない |
| Metric | 指標定義（カタログ §2.1 で 14 指標が定義済み。既存店売上前年比 / 客数 / 客単価 / インバウンド売上 / CPI / EC 市場規模 等） | カタログから読込。システムは生成しない |
| SourceArticle | 出典記事（URL 一意） | 初出掲載日に生成、以後不変。掲載日は追記される |
| DigestFile | 取り込み元の日次ダイジェスト MD | ファイル走査時に生成・更新 |
| Observation | 業態 × 期間 × 指標 × スコープ の観測値 | upsert。natural key で一意 |
| ExtractionCache | URL 単位の抽出結果キャッシュ | LLM 抽出時に生成、以後不変 |
| UnresolvedRow | 構造化に失敗した行 | 実行ごとに再評価。解決したら削除 |
| ExtractionRun | 実行メタデータ | 実行ごとに追記 |

### 4.2 主要テーブル定義

#### segments（カタログ由来・読み取り専用）

| カラム | 型 | 制約 | 説明 |
|--------|-----|------|------|
| segment_id | string | PK | kebab-case。例: shopping-center, department-store, convenience-store |
| name | string | not null | 表示名。例: ショッピングセンター |
| aliases | string[] | not null | 記事タイトル中の別表記。例: `SC`, `商業施設` |
| parent_segment_id | string | nullable | 上位業態（例: 食品スーパー → 小売全体） |
| entity_type | enum | not null | association（協会統計） / company（個社） / macro（マクロ経済統計） |
| source_authority | string | not null | **既定の発表主体コード**。カタログ「発表主体」列から IF-02 の発表主体対応表で解決する。例: `chain-store-association`, `meti`, `mic`。observations の同名フィールドの既定値になる |
| display_order | int | not null | 画面上の表示順 |

#### metrics（カタログ由来・読み取り専用）

| カラム | 型 | 制約 | 説明 |
|--------|-----|------|------|
| metric_id | string | PK | **カタログ §2.1 の KPI ID をそのまま使用する**。全 14 件: `existing-store-sales-yoy` / `all-store-sales-yoy` / `sales-amount-absolute` / `customer-count-yoy` / `spend-per-customer-yoy` / `inbound-sales-yoy` / `domestic-customer-sales-yoy` / `inbound-customer-count-yoy` / `sales-amount-yoy` / `store-count-yoy` / `operating-profit-yoy` / `operating-revenue-yoy` / `cpi-yoy` / `ec-market-size-yoy` |
| name | string | not null | カタログの「正式名称・別名」列。例: 既存店売上高（前年同月比） |
| unit | enum | not null | percent_yoy / percent / jpy_oku / count / index の 5 値（カタログ §4.4 と同一。「単位」列との対応は IF-02 の単位対応表を参照） |
| value_type | enum | not null | ratio（前年比などの変化率） / absolute（金額・件数の実数） |
| direction_hint | enum | not null | higher_is_better / lower_is_better / neutral（`cpi-yoy` は neutral） |
| aliases | string[] | not null | 記事中の別表記。例: `既存店売上高`, `既存店` |
| default_scope | enum | nullable | existing_store / all_store / total_supply / n_a（カタログ「既存店/全店」列との対応は IF-02 のスコープ対応表を参照） |
| precision | int | not null | 小数第何位まで保持するか |

**natural key**: `(segment_id, metric_id, scope, period_key, source_authority)`。この 5 項の組が一意であることが冪等性の根拠となる。

`source_authority` を含める理由は、同一の業態・指標・期間であっても発表主体が異なれば**母集団が異なる別の量**だからである（カタログ §1.1 / §3-8 / §1.4）。例えば `百貨店 6月 既存店` は日本百貨店協会（会員社ベース）と経済産業省 商業動態統計（全国調査ベース）の双方から発表されうるが、両者の数値は一致しないことが常態であり、一方が他方を上書きすると誤ったデータが混入する。4 項キーではこの上書きを検知できないため、設計工程での発見を受けて 5 項に拡張した（7-14）。


- segments / metrics は本システムが書き込まない。カタログ MD が単一の真ソースであり、システムは参照するだけ（FR-03 / FR-24）

| 項目 | 方針 |
|------|------|
| 技術スタック | ビルドツールを使わない素の HTML + CSS + JavaScript。チャートは Chart.js のソースを HTML にインライン埋め込み（NFR-08） |

### IF-02 カタログスキーマ契約

小売ドメイン室が作成するカタログ MD は、パーサが機械的に読み取れるよう以下を満たすこと。**指標の増減は本システムのコード変更を伴わない**（NFR-09）。

#### 見出し検出条件

カタログ側の見出しは章番号を含む（実体は `## 1. 業態区分マスタ` / `## 2. KPI 定義`）。パーサは **番号や語尾に依存しない部分一致**でセクションを特定する。カタログ側の見出し番号・語尾の変更を本システムの改修理由にしない。

| 対象 | 検出条件 | カタログ実見出し |
|------|---------|-----------------|
| 業態定義 | H2 の見出しテキストに `業態区分` を含む | `## 1. 業態区分マスタ` |
| 指標定義 | H2 の見出しテキストに `指標定義` または `KPI 定義`（半角空白の有無を問わず `KPI定義` も可）を含む | `## 2. KPI 定義` |

- 検出した H2 の配下（次の H2 まで）にある最初の MD テーブルを定義表として読む。H3 の小見出し（`### 1.1 業態一覧` / `### 2.1 KPI 一覧`）を挟んでも良い
- 条件に一致する H2 が 0 個または 2 個以上の場合はエラー停止する（FR-24 と同じ扱い。曖昧なまま読み進めない）

#### 列要件

列名は複数の許容名を受理する。カタログ側の列名変更を本システムの改修理由にしない。

**業態定義表の必須列**

| 用途 | 許容列名 | 対応する segments 属性 |
|------|---------|----------------------|
| 業態 ID | `segment_id` / `業態ID` | segment_id |
| 名称 | `名称` / `正式名称` | name |
| 別名 | `別名` / `表記ゆれ` | aliases |
| 種別 | `種別` | entity_type（association / company / macro） |
| 発表主体 | `発表主体` | source_authority（下記 発表主体対応表で変換） |
| 表示順 | `表示順` | display_order |

- 任意列: `上位業態`（parent_segment_id、nullable）。存在しない場合は null を補う

**指標定義表の必須列**

| 用途 | 許容列名 | 対応する metrics 属性 |
|------|---------|---------------------|
| KPI ID | `metric_id` / `KPI ID` | metric_id |
| 名称 | `名称` / `正式名称` | name |
| 別名 | `別名` / `表記ゆれ` | aliases |
| 単位 | `単位` | unit（下記 単位対応表で変換） |
| 値種別 | `値種別` | value_type（ratio / absolute） |
| 方向 | `方向` | direction_hint（higher_is_better / lower_is_better / neutral） |
| 既定スコープ | `既定スコープ` / `既存店/全店` | default_scope（下記 スコープ対応表で変換） |
| 小数桁 | `小数桁` | precision |

- 必須列が 1 つでも欠けている場合はエラー停止する（FR-24）。欠損列を既定値で埋めて処理を続行しない
- 別名は 1 セル内に区切り文字（読点 / カンマ / スラッシュ）で列挙する。記事タイトルに現れる表記を列挙する（例: `existing-store-sales-yoy` → `既存店売上高, 既存店売上, 既存店`）
- `segment_id` / `metric_id` は kebab-case で一意。既存 ID の意味を変更する改名を行わない（改名は新 ID の追加 + 旧 ID の非推奨マークで表現する）
- カタログに存在しない ID をパーサが暗黙生成することはない（FR-24）

#### 単位対応表

unit の enum は **percent_yoy / percent / jpy_oku / count / index の 5 値**（カタログ §4.4 と同一）。

セル値は区切り文字（`/` / 読点 / カンマ）で複数表記を含みうるため、**セル内トークンごとに照合**する（カタログ §2.1 の `sales-amount-absolute` は実セルが `億円 / 兆円`）。

| カタログ「単位」列のセル内トークン | 本システムの unit | value_type | 変換 |
|-----------------------------------|------------------|-----------|------|
| `%`（全角 `％` を含む） | percent_yoy | ratio | 増 → 正、減 → 負。全角％・半角% の双方を受理（FR-05） |
| `億円` | jpy_oku | absolute | そのまま格納 |
| `兆円` | jpy_oku | absolute | **億円に換算して格納**（×10,000）。表示時に単位を再選択する |
| 空欄 / `—` | — | — | 単位を要する指標で空欄の場合はエラー停止（FR-24） |

- 1 セルに `億円` と `兆円` が併記される場合、格納単位は jpy_oku に一本化し、記事側の表記に応じて取り込み時に換算する
- unit の `percent` / `count` / `index` は現行カタログの 14 指標では未使用。将来指標のために enum に残す
  - `percent`: 非 YoY の静的比率・シェア型指標用（例: EC 化率、インバウンド比率）
  - `count`: 店舗数の絶対値用（`store-count-yoy` は伸び率のみのため現状不要）
  - `index`: CPI などの指数水準そのもの用（`cpi-yoy` は前年同月比のみのため現状不要）

#### 発表主体対応表

`source_authority` は natural key の構成要素であるため、自由記述の日本語ではなく **kebab-case のコード**として保持する。カタログ「発表主体」列のセルは注記を含むため（例: `業界紙（DCS）集計（協会名は記事本文未確認。※業界一般知識による補足＝日本DIY・ホームセンター協会）`）、**先頭トークン**（最初の `（` / `／` より前）で照合する。

### 補足 A: 実装言語の選定

| 観点 | Python（採用候補） | Node.js | Bash |
|------|-------------------|---------|------|

| 再現率 | タイトル表現の多様性に弱い。`51カ月ぶりに前年割れ` のような叙述表現を取りこぼす | 高い | 決定論で大半を処理し、残りを LLM が救う |
| コスト | ゼロ | 588 行 + 日次数行の継続課金 | 未解決行のみ。キャッシュヒット率 95% 想定（NFR-11） |
| 実行時間 | 数秒 | 行数に比例して増大 | NFR-01 の 60 秒以内に収まる |
| 保守性 | 表現追加のたびにルール追加が必要 | プロンプト調整が効くが、変更の影響範囲が読めない | ルール追加で決定論側のカバー率を上げるほど LLM 依存が減る、改善方向が明確 |
| 監査性 | 抽出根拠が正規表現として明示される | 根拠が不透明 | extraction_method で由来を区別でき、画面上でも識別できる（SC-02） |

**選定: 二段ハイブリッド（決定論ファースト + LLM フォールバック + URL 単位キャッシュ）**。この構成の要点は、LLM の非決定性を「キャッシュに閉じ込める」ことで再現性と冪等性を守る点にある。LLM は新規記事に対して 1 回だけ働き、以後は決定論的な参照になる。
